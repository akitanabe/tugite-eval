> 実際のレスポンスを見ているのですが、応答内容が口語的に説明すぎますね。自分としてはある単位の処理をコードでまとめて示し何をやっているか説明してもらうぐらいのイメージなのですが

ユーザーは続いて目的を「はい、自分で書かないとつながりというのが見えにくいのでそこを追いやすくするという狙いです」と補足した。

これは新しい仕様入力としてprospectiveに適用する。親から、旧candidate
`2e7ae9237103cc9a6c6d9afbb748c11ad2ea51e7` の14件は旧基準でPASSだったがユーザー期待との差があった、

旧 [round 004](../../rounds/explain-398-004/HANDOFF.md)、旧fixture/rubric/resultsは保持し、遡及して合否を変更しない。

## 新しい期待

実在する関数・class・構造体等を流れの骨格にし、呼出し・処理順・データ受渡しをつないで示す。
構造が追える実コード抜粋を並べ、その内部処理を短く補足する。
位置名一覧や長い散文だけでは達成としない。単なる全コードdumpも目的ではない。
まとまった抜粋は一つの関数全体に限定しない。必要な一部分を選べるが、実在の要素とその境界・呼出し関係を保つ。
複数関数/ファイルにまたがる場合も実コード構造に沿って出典と省略を明示する。
架空の概念的工程を先に作って実装を過剰に再編しない。全関数一覧/import一覧にもせず、対象機能に関係する実装要素を選ぶ。
架空の合成関数・擬似コードを実在と偽らない。注釈・図・短い接続説明も許すが、主な実コード抜粋の代替にはしない。

目的は自分で実装していないHumanが処理間のつながりをコードで追えること。
入力値→判断/変更→次へ渡す値・呼出先を読み順に追えるように選び、孤立した抜粋列挙にしない。
文章は接続と省略を補助し、全呼出しdumpに戻さない。

抜粋の必要十分性を、重要な判断・順序・状態・データ受渡し・副作用・tx・失敗・接続を追えるかで評価する。
抜粋の行数、fence数、文量比率、特定の章立て・語句・唯一の抜粋集合をoracleにしない。
短い回帰fixtureでは全関数が必要十分な抜粋になり得るため、全関数提示を機械的にdumpと扱わない。
未提供adapterや実装のない接続をコードで補わせない。

さらにユーザーは「引数とかもゼロイチで全て解説する必要はありません。あくまで内部で行っている処理に絞ってください」と範囲を明確化した。
引数一覧・型・デフォルト値・全入力の網羅説明を追加しない。値/引数の補足は内部の重要な分岐・状態変更・受渡しを
理解するために必要な箇所だけ、コードに沿って短く示す。入力から出力までの接続説明をAPIリファレンス化しない。
引数解説の量によって加点しない。この補足も新candidate到着前の仕様入力として記録する。

追加の粒度優先順位として、見て分かる引数や単純代入の逐語説明へ情報を割かず、コードをまたぐ接続、
重要な分岐・状態変化・実行順序へ説明量を集中する。コードを読む理解を補助し、一行ずつ日本語へ翻訳しない。
ユーザーの原文「そうですね、引数とかの見てわかるものに情報をあまり割かないでください。コ」の
末尾「コ」は未完として保持し、補完しない。接続等への集中は親の明示補足として記録し、
新たな網羅項目や文量の機械判定を増やすものではない。

## 最新の骨格基準と優先順位

ユーザーは「あとは説明の際は関数やclass、構造体などを基準に流れを組み立ててください。コードを基準にとはそういう意味で言っています」と明確化した。
この最新指示を元Issueの「主要単位はclass/fileではなく意味処理」より優先する。コード抜粋を概念工程に添えるだけでは達成しない。
旧baselineには歴史的な`398-process-and-effects`を保持し、新candidateにはその矛盾する骨格条件を適用しない。
新candidateの`398-code-structure-and-effects`で実在するController.exchange→SessionOperation.exchange→MemoryStoreの接続を軸にし、
従来のtx/拒否/副作用/失敗境界を保持する。`code-centered-explanation`も実装構造の骨格に合わせて明確化した。
共通基盤が挙動に効く場合と基盤自体が対象の場合の扱いは維持する。
